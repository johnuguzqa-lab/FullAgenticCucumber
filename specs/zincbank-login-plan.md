## Target application (inspected live)

- URL: `https://zincbank.cydeo.io/login` · Title: _Log in · ZincBank_
- Heading: **"Sign in to ZincBank"** · intro **"Welcome back"**

### Confirmed real locators (priority-ordered per framework rules)

| Element             | Recommended locator                              | Fallback (`data-testid`*)                           |
| ------------------- | ------------------------------------------------ | --------------------------------------------------- |
| Email               | `getByLabel('Email')`                            | `login-email-input` (placeholder `you@example.com`) |
| Password            | `getByLabel('Password')`                         | `login-password-input`                              |
| **Sign in**         | `getByRole('button', { name: 'Sign in' })`       | `login-submit`                                      |
| Message region      | `getByRole('note')` / `getByText(...)`           | `login-error`                                       |
| **Open an account** | `getByRole('link', { name: 'Open an account' })` | `login-apply-link` → `/apply`                       |
| Main container      | —                                                | `login-page`                                        |

### Confirmed observable behaviors (from live browser)

- **Valid credentials from `.env` (`USERNAME`/`PASSWORD`)** → Supabase auth returns **200** and the app lands on **`https://zincbank.cydeo.io/dashboard`**.
- **Well-formed email + wrong password** → the `note` region changes to **"Invalid email or password."**; stays on `/login`.
- **Empty fields** → no navigation; the `note` keeps the default hint **"Enter your email and password."** (no distinct empty-field error).
- **Malformed email** (e.g. `not-an-email`) → no navigation; hint remains (no client-side format validation).
- Invalid-login attempt emits an expected **400** from Supabase → harmless; `consoleErrors` are only attached to failure artifacts, so it will not fail the scenario.

## ⚠️ Critical integration caveats (hand these to the Test Generator)

1. **Test-id attribute mismatch.** The framework registers `selectors.setTestIdAttribute('data-test')` in `src/hooks/hooks.ts` (BeforeAll) for Saucedemo. **ZincBank uses `data-testid`**, so `getByTestId(...)` will NOT resolve on ZincBank as configured. → **Prefer `getByLabel` / `getByRole` / `getByText`** (app-agnostic and match locator-priority rules); do not depend on `getByTestId` without first addressing the per-app attribute registration.
2. **Error region is role `note`, NOT `alert`.** The existing step `a login error message {string} should be displayed` (uses `getByRole('alert')`) must **not** be reused as-is for ZincBank — a new step targeting `getByRole('note')` is required.
3. **The hint text is always present.** Do not assert "no error" by checking the note is empty — it always holds _"Enter your email and password."_. Assert on the **specific message text**.
4. **Existing `LoginPage`/`login.steps.ts` are Saucedemo-specific** (Username label, "Login" button, alert role, `/inventory.html`) and do not match ZincBank. Create a new page object + thin steps following the same conventions (BasePage, CustomWorld, `config.username`/`config.password`), rather than reusing them.
5. **Auth rate-limiting observed** on rapid repeated logins → rely on `retries` (CI=1) and avoid hammering the auth endpoint within one suite run.

## Feature: ZincBank Login

**Preconditions:** `USERNAME` and `PASSWORD` set in `.env` (verified present); `config.baseUrl` = ZincBank (run with the appropriate `ENV`).

### Scenario 1 — Successful sign-in with valid credentials

- Priority: **Critical** · Tag: `@smoke @critical`
- **Given** I open the ZincBank login page
- **When** I sign in with the configured valid credentials
- **Then** I am redirected to the ZincBank dashboard (`/dashboard`)

### Scenario 2 — Sign-in with invalid credentials

- Priority: **High** · Tag: `@regression @critical`
- **Given** I am on the ZincBank login page
- **When** I sign in with an invalid email and password
- **Then** I see the login message **"Invalid email or password."**
- **And** I remain on the ZincBank login page

### Scenario 3 — Submit with empty fields

- Priority: **Medium** · Tag: `@regression`
- **Given** I am on the ZincBank login page
- **When** I submit the form with empty email and password
- **Then** no navigation occurs and I see the hint **"Enter your email and password."**

### Scenario 4 — Submit with a malformed email

- Priority: **Medium** · Tag: `@regression`
- **Given** I am on the ZincBank login page
- **When** I enter a malformed email and a password, then submit
- **Then** no navigation occurs and the hint remains visible

### Scenario 5 — "Open an account" navigates to `/apply`

- Priority: **Medium** · Tag: `@smoke`
- **Given** I am on the ZincBank login page
- **When** I click the "Open an account" link
- **Then** I am on the ZincBank account-opening page (`/apply`)

### Scenario 6 — Login page renders correctly

- Priority: **Low** · Tag: `@sanity`
- **Given** I open the ZincBank login page
- **Then** the heading "Sign in to ZincBank", the Email field, the Password field, and the "Sign in" button are visible
- **And** the "New to ZincBank? Open an account" link is visible

> **Optional follow-up (outside pure login flow):** _Logout returns to login_ — requires inspecting the dashboard's logout control during generation (dashboard inspection was rate-limited during planning).
